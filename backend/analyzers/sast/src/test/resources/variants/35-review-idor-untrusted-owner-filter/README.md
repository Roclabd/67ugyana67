# IDOR: фильтр владельца, управляемый клиентом

- Находка: `TicketLookup.kt:28–30`. И ticketId, и customerId берутся из запроса. Для чтения чужой заявки достаточно подставить её ID и её customerId; аутентификация атакующего их не ограничивает.
- Контроль: `TicketLookup.kt:35–39`. Тот же параметризованный SQL связывает customer_id с authentication.name из серверной сессии.
- Причина FN: `DataAccess.filtersByOwner` проверяет лишь наличие owner-колонки в WHERE, не происхождение значения, с которым она сравнивается. `ObjectAuthorizationRule` исключает такой сток из кандидатов.
- Оба SQL-запроса параметризованы: это проверка object-authorization, а не SQL injection.

Проверено на текущих исходниках анализатора: FN=1, FP=0, контроль проходит. `expected.json` описывает правильный результат, поэтому этот регрессионный тест сейчас должен падать.
