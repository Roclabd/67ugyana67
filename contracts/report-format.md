# Формат отчётов

> Версия 1. Спецификация экспорта — [формат авторов набора](../fixtures/training/docs/submission-format.md).

Из одного набора находок (`contracts/finding.schema.json`) `ReportExporter` строит три отчёта.

## Внутренний отчёт

- Порт `FINDINGS` передаёт список объектов `$defs/finding`. `NodeOutput.coverage` анализатора соответствует `$defs/coverage`. Порт `REPORT` и поле `report` в API запуска используют корневую структуру схемы. Необязательные поля без значения опускаются.
- `inputHash` привязывает отчёт к точному коммиту или снимку файлов. Для запуска сценария также сохраняются `workflowId` и `workflowVersion`. `rulesVersion` идентифицирует набор правил и версию справочника SCA. Если получение входа завершилось ошибкой до определения снимка, API показывает ошибку запуска без отчёта. `sourceSubdir` сохраняет выбранную подпапку Git-репозитория для привязки внешних аннотаций.
- `coverage.byAnalyzer` содержит записи по идентификаторам нод. Общий статус — худший среди требуемых проверок: `COMPLETE` < `PARTIAL` < `FAILED`. Пропуск неактивной ветки допустим. Упавшая обязательная нода даёт `FAILED`, отсутствующее покрытие обязательной проверки даёт как минимум `PARTIAL`. Если ни один анализатор не выполнился, покрытие не может быть `COMPLETE`. История и CI берут `coverageStatus` из `coverage.status`. Для строгого успеха CI нужен завершённый запуск и отчёт с `COMPLETE`.

Доставка уведомлений (`notify.*`) в покрытие не входит: сбой отправки не меняет `coverage.status` и статус запуска, исход описывает отдельное поле `delivery` запуска (см. docs/API.md). Покрытие считают только ноды источника и анализаторы.
- `rulesApplied` перечисляет идентификаторы применённых правил. Необязательный `rules` описывает те же правила объектами с `id`, `title` и `description`. В старых отчётах могут быть только идентификаторы. `springBootBoms` в покрытии SCA перечисляет релизы встроенных BOM и места их подключения, если по ним определены версии. У узлов разбора и карты маршрутов каталог доступен в покрытии узла.
- Встроенный SCA в `dependencyCoverage` считает объявления с числовой версией, сверенные с записями (`checked`), объявления с числовой версией без записей (`withoutAdvisories`) и объявления без установленной или поддерживаемой версии (`unresolvedVersion`). Каждое разобранное объявление учитывается один раз. В `advisorySources[].snapshotDate` сохраняется дата снимка справочника, если она указана и корректна. В Markdown видны счётчики и даты. Общий статус определяется прежними условиями.
- `filesSkipped` содержит файлы, которые анализатор пропустил, с причинами. `unresolved` содержит факты, которые не удалось установить. Если такой факт нужен для проверки в её заявленной области, покрытие как минимум `PARTIAL`. `dismissed` содержит проверенные кандидаты, отклонённые по известной причине.
- `fingerprint` — SHA-256 однозначно сериализованных категории, класса (для SCA — координат с версией и канонического `advisoryId`), пути, нормализованного фрагмента и SHA-256 исходных байтов файла. Отпечаток рассчитывается внутри анализатора. Внешние представления отчёта, включая API, SSE и запросы к LLM, исключают `secretHash` и необработанные значения секретов.

## 1. JSON авторов набора

`{"findings": [...]}`, UTF-8, без комментариев и висячих запятых. Экспорт включает только поля из таблицы. Необязательные поля без значения опускаются.

| Категория | Поля |
|---|---|
| SECRET | `category`, `path`, `class`, `line`, `endLine`?, `severity`?, `description`?, `remediation`? |
| SAST | то же, что SECRET |
| SCA | `category`, `path` (= `build.gradle.kts` или другой файл объявления), `group`, `artifact`, `version`, `advisoryId`, `severity`?, `description`?, `remediation`? |

Правила:
- `line`, `endLine` — целые JSON-числа от 1, `line ≤ endLine ≤ line + 14`. Для одной строки достаточно `line`. Код проверяет соотношение границ перед экспортом.
- `path` — относительно корня проверяемого проекта, с `/` и точным регистром. Обязательные строки содержат хотя бы один непробельный символ.
- SCA: одна находка = одна уязвимость; если CVE и GHSA описывают одно и то же — один `advisoryId` (берём CVE из `aliases`, если есть).
- Значения секретов не попадают ни в `description`, ни куда-либо ещё.
- Нода пользовательского правила SCA записывает в `advisoryId` локальный идентификатор `POLICY-…`, полученный из координат и диапазона версий.
- Перед экспортом канонизируем `advisoryId` и убираем повторы. Ключ для SECRET/SAST включает категорию, путь, класс и диапазон строк. Для SCA ключ включает категорию, путь, группу, артефакт, версию и канонический `advisoryId`.
- Сортируем по категории (SECRET, SAST, SCA), пути и затем по полям ключа категории. Для SECRET/SAST порядок внутри пути: `line`, `endLine` (или `line`), класс. Для SCA: группа, артефакт, версия, `advisoryId`. Один набор результатов даёт одинаковый JSON байт в байт.
- Если находок нет: `{"findings": []}`.

## 2. Читаемый отчёт (Markdown / HTML / таблица в интерфейсе)

Для каждой находки: категория, название, краткое описание своими словами, место (SECRET/SAST — файл и строки; SCA — файл объявления, координаты с версией, CVE/GHSA), критичность, рекомендация. Секреты — маской. Образец — [`fixtures/training/ground-truth/training-findings.md`](../fixtures/training/ground-truth/training-findings.md).

Обязательные дополнительные разделы:
- **Покрытие:** общий статус `COMPLETE` / `PARTIAL` / `FAILED`, по каждому анализатору — разобрано файлов, пропущено (почему), что не установлено (`unresolved`), какие правила применены (если есть `rules`). При `PARTIAL`/`FAILED` первая строка отчёта говорит об этом прямо; «0 находок» при неполном анализе не выглядит как успех.
- **AI:** статус объяснений (`OK` / `PARTIAL` / `NOT_RECEIVED`), модель и счётчики валидатора, когда известны. Если секция `ai` отсутствует, отображаем `NOT_RECEIVED`.
- **Отклонённые безопасные места** (`dismissed`) — сворачиваемый список с причинами.

## 3. SARIF 2.1.0

`GET /api/runs/{id}/report.sarif` возвращает файл `report.sarif` с типом `application/sarif+json`. В файле каждый результат ссылается на описание правила и место в исходном файле. Уровни `CRITICAL` и `HIGH` отображаются как `error`, `MEDIUM` — как `warning`, `LOW` — как `note`. [Формат для GitHub Code Scanning](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support).

Пути даны относительно корня снимка. Если в отчёте сохранена подпапка Git-репозитория (`sourceSubdir`), она добавляется к пути. Строки начинаются с 1. У находок без номера строки сохраняется ссылка на файл. В файл входят описания правил, координаты и отпечатки находок. GitHub может рассчитать собственные отпечатки по файлам репозитория при загрузке. Для `PARTIAL` и `FAILED` поле `invocations[].executionSuccessful` равно `false`, а исходный статус сохраняется в `properties.coverageStatus`.
